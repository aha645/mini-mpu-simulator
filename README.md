# Mini NPU Simulator

## 실행 방법

```
python main.py
```

실행하면 모드를 선택합니다.

- `1`: 사용자 입력 모드 — 3×3 필터 A, B와 3×3 패턴을 한 줄씩(공백 구분) 입력받아 MAC 점수를 비교
- `2`: data.json 분석 모드 — `data.json`(필터: size_3/5/13/25, 패턴: 각 크기별 2개)을 읽어 일괄 판정

`data.json`은 `main.py`와 같은 디렉터리에 있어야 합니다(`load()`의 기본 경로가 `"data.json"`).

## 구현 요약

### 라벨 정규화

data.json에는 필터 키가 `cross`/`x`, 패턴의 `expected` 값이 `+`/`x`처럼 서로 다른 표기가 섞여 있습니다. `normalize_label()`이 이를 모두 표준 라벨 `Cross`/`X`로 통일하고, 알 수 없는 라벨이 들어오면 `ValueError`를 던집니다. `normalize_patterns()`는 이 예외를 잡아 `expected=None`으로 처리하면서 원본 값을 `expected_raw`에 남겨, 실패 원인 메시지에서 어떤 값이 문제였는지 확인할 수 있게 합니다.

### MAC 연산

`mac_score()`는 외부 라이브러리 없이 이중 for문으로 패턴과 필터를 위치별로 곱해서 누적합니다(Multiply-Accumulate). 필터가 N×N이면 연산 횟수는 N²입니다.

### 동점(epsilon) 처리 정책

`judge()`는 `abs(score_cross - score_x) < 1e-9`이면 `UNDECIDED`를 반환합니다. 부동소수점 연산은 근본적으로 오차가 있어서 두 점수가 수학적으로 같아도 `==` 비교에서는 다르다고 나올 수 있습니다. `1e-9` 허용오차 안이면 "동점"으로 간주해 이 문제를 피합니다.

### 필터·패턴 크기 검증

`mode2_run()`은 MAC 연산을 하기 전에 (1) 패턴 크기에 해당하는 필터가 data.json에 존재하는지, (2) 패턴과 `Cross`/`X` 필터의 행·열 수가 일치하는지를 먼저 검사합니다. 둘 중 하나라도 어긋나면 해당 케이스만 FAIL 처리하고 다음 케이스로 넘어가며, 프로그램 전체는 중단되지 않습니다.

## 결과 리포트

### 실행 결과 요약 (data.json 기준)

총 테스트: 8개 / 통과: 4개 / 실패: 4개

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_3_1 | 0.50 | 0.50 | UNDECIDED | X | FAIL |
| size_3_2 | 4.50 | 0.10 | Cross | Cross | PASS |
| size_5_1 | 0.90 | 0.90 | UNDECIDED | X | FAIL |
| size_5_2 | 8.90 | 0.10 | Cross | Cross | PASS |
| size_13_1 | 0.30 | 14.70 | X | X | PASS |
| size_13_2 | 7.50 | 7.50 | UNDECIDED | Cross | FAIL |

### 실패 원인 분석

실패 케이스는 데이터/스키마 문제, 로직 문제, 수치 비교 문제 세 가지로 분류해서 진단하도록 구현했습니다.

- **데이터/스키마 문제**: 패턴 크기에 맞는 필터를 data.json에서 찾을 수 없거나, 패턴과 필터의 크기가 다르거나, `expected` 라벨 정규화에 실패한 경우. 현재 data.json은 모든 필터가 정상 로드되고 크기·라벨이 전부 일치해서 이 유형의 실패는 없습니다.
- **수치 비교 문제**: `judge()`가 `UNDECIDED`를 반환한 경우. 현재 FAIL 4건(`size_3_1`, `size_5_1`, `size_13_2`, `size_25_1`)이 전부 이 유형입니다. 위 표를 보면 이 케이스들은 Cross 점수와 X 점수가 정확히 같도록(0.50/0.50, 0.90/0.90, 7.50/7.50, 4.90/4.90) 설계돼 있어서, `judge()`가 정의상 `UNDECIDED`를 반환하고 프로그램 규칙상 무조건 FAIL로 처리됩니다. 즉 MAC 연산이나 필터 데이터가 잘못된 것이 아니라 "동점이면 판정 불가"라는 비교 정책 자체가 낳는 의도된 결과입니다.
- **로직 문제**: 크기·라벨이 모두 정상이고 동점도 아닌데 판정이 `expected`와 다른 경우. 현재는 발생하지 않았습니다.

크기 불일치, 필터 누락, 라벨 오류를 data.json에 인위적으로 추가해 테스트한 결과 프로그램이 크래시 없이 해당 케이스만 "데이터/스키마 문제"로 FAIL 처리하고 나머지 케이스를 계속 진행하는 것을 확인했습니다. 실패가 0건이 아니라 4건인 이유는 데이터 오류가 아니라, 애초에 동점으로 설계된 테스트 패턴과 epsilon 기반 비교 정책이 만나서 나온 결과입니다.

### 성능 표 해석 및 시간 복잡도(O(N²))

| 크기 | 평균 시간(ms) | 연산 횟수 |
|---|---|---|
| 3×3 | 0.002 | 9 |
| 5×5 | 0.004 | 25 |
| 13×13 | 0.023 | 169 |
| 25×25 | 0.079 | 625 |

(위 시간 값은 `time.perf_counter()`로 측정한 실측치라 실행 환경·시스템 부하에 따라 매 실행마다 조금씩 달라질 수 있습니다. "연산 횟수" 열은 N²로 고정된 값이라 항상 동일합니다.)

`mac_score()`는 N×N 필터의 모든 칸을 한 번씩 순회하며 곱하고 더하므로, 연산 횟수는 정확히 N²입니다(표의 "연산 횟수" 열과 일치). 크기가 3→5→13→25로 커질 때 연산 횟수는 9→25→169→625로, 변의 길이(N)의 제곱에 비례해서 늘어납니다.

측정된 시간의 증가율은 연산 횟수 증가율보다 완만합니다: 3×3 대비 25×25는 연산 횟수가 약 69배 늘어나지만, 평균 시간은 약 38배(0.0021ms → 0.0808ms) 늘어나는 데 그칩니다.

택시 요금(기본요금 + 거리요금)에 비유하면 이해하기 쉽습니다. 측정 시간 = **고정비용**(함수 호출, 반복문 진입 등 매번 드는 준비 시간) + **진짜 연산 비용**(곱셈·덧셈, N²에 비례)으로 이루어져 있습니다.

- 짧은 거리를 타면 기본요금이 요금 대부분을 차지해서, 거리가 2배가 돼도 요금은 2배가 안 됩니다. 마찬가지로 3×3(연산 9번)은 계산량 자체가 워낙 적어서, 실제 곱셈·덧셈 시간보다 "함수를 호출하고 반복문을 도는" 준비 시간(고정비용) 비중이 더 큽니다. 그래서 25×25로 연산 횟수가 69배 늘어도 시간은 38배만 늘어나는 것입니다 — 고정비용은 크기가 커져도 같이 늘어나지 않으니 전체 증가율을 눌러버리는 셈입니다.
- 먼 거리를 타면 기본요금 비중이 작아지고 거리요금이 요금을 좌우해서, 거리와 요금이 거의 비례합니다. 마찬가지로 13×13(연산 169번)과 25×25(연산 625번)는 둘 다 계산량이 이미 꽤 커서 고정비용 비중이 상대적으로 작습니다. 그래서 이 구간만 보면 연산 횟수는 약 3.7배, 시간도 약 3.5배로 훨씬 더 정비례에 가깝게 나옵니다.

즉 O(N²) 법칙이 틀린 게 아니라, 크기가 작을 땐 고정비용이 섞여서 비율이 흐려지고, 크기가 커질수록 진짜 N² 계산량이 시간을 지배하면서 이론값에 가까워지는 것입니다.
